# Organization API gap and minimal backend proposal

This is an unimplemented proposal requiring backend/security review. None of the proposed routes below exists in inspected backend main `74467a4e68b480387ca1ff16516feca4afb1d095` (October 12, 2026). Frontend organization capability remains unavailable.

## Source-verified behavior

Paths below are relative to `backend/src/main/java/com/wautech/crm/`.

- `identity/controller/AuthenticationController.java`: GET `/api/auth/csrf` returns headerName/parameterName/token; POST `/api/auth/login` takes email/password and returns identity; GET `/api/auth/me` returns id/email/firstName/lastName; POST `/api/auth/logout` invalidates session and returns 204.
- `identity/service/AuthenticationService.java`: bcrypt's 72-byte password bound, authentication manager, change-session-ID strategy, saved Spring SecurityContext and security audit. Login response alone does not verify browser cookie continuity.
- `platform/security/SecurityConfiguration.java`: session-backed CSRF repository, X-CSRF-TOKEN; csrf GET and login POST permit anonymous access but login POST still requires CSRF. Other auth routes require authentication. Form login/basic/default logout disabled. Method security enabled. No browser CORS policy established.
- `platform/security/UserEnabledSessionFilter.java`: persisted enabled-user checks for existing session. `platform/security/ActiveOrganizationContextFilter.java` exempts auth routes; CRM requests require X-Organization-ID. Missing header or absent active membership is 403; malformed UUID is 400. Unknown/archived organization and disabled/missing user cannot establish active context. Trusted request attribute is set only after membership validation.
- `platform/tenant/AuthenticatedOrganizationContext.java`: request scoped, requires the trusted UUID attribute. CRM services query within that organization and validate related entities; no client-provided role establishes authorization.
- `platform/security/CrmAuthorization.java`: persisted enabled user, non-archived organization, ACTIVE membership and trusted context matching the target organization are required. `organization/entity/OrganizationRole.java`: all four roles view; OWNER/ADMIN/SALES_USER write; only OWNER/ADMIN manage; import restricted to OWNER/ADMIN. Ownership transfer and role assignment have further restrictions.
- `organization/service/OrganizationService.java`: get/update/archive require canManageOrganization; create/require/lock are internal service operations, not self-discovery APIs.
- `organization/service/OrganizationMembershipService.java`: listByOrganization/listByUser/get/create/transition/changeRole require canManageOrganization. Ownership transfer requires OWNER; no self role change, no removal/demotion of last active owner, constrained role assignment. Do not expose these methods through relaxed authorization.
- `organization/entity/OrganizationMembership.java`: unique organization/user pair, default INVITED/VIEWER; ACTIVE, SUSPENDED, REVOKED lifecycle; association with one organization/user. Roles are tenant scoped. `organization/repository/OrganizationMembershipRepository.java` has tenant-specific lookups and user/status/role lookup, but no all-role active-user discovery query.
- `backend/src/main/resources/application.yml`: WAUTECH_SESSION, HttpOnly, SameSite=Lax, Secure configurable (default false), 30-minute idle timeout. Production cookie attributes require deployment verification.

## Proposed HTTP contracts

Keep selection request scoped using the existing organization header. No new session-global selected organization field or switch mutation is needed; this avoids one browser tab silently changing another tab's tenant.

| Proposed route                                            | Purpose and response                                                                                                            | Authorization                                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| GET `/api/auth/organizations`                             | Array of `{organizationId, organizationName, membershipId, role, status: "ACTIVE"}` for current user only; empty array is valid | Session, enabled persisted principal; ACTIVE memberships and non-archived organizations only; no organization header |
| GET `/api/auth/organizations/{organizationId}/membership` | Same minimal self-membership DTO for one requested UUID                                                                         | Session plus fresh enabled-user/active-membership/non-archived-org validation; no organization header                |

These paths deliberately live under the existing auth bootstrap exemption. They must still enforce principal-scoped database checks in their own service. No userId, role, status, arbitrary membershipId or selected organization is accepted from the client. Membership DTO reveals only the caller's own membership, not a directory of users or internal entity fields. Use 401 for absent/invalid/disabled sessions, 400 for malformed UUID, and one generic 403 for unknown, archived or inaccessible organizations to avoid existence disclosure. Add no-store response headers and bounded/rate-controlled discovery; choose pagination before exposing unbounded production membership sets if necessary.

Selection: list accessible organizations, then fetch the selected self-membership route to validate current access. Only after successful validation may the host create a CRM client with that organization UUID. This validation does not grant durable authority: every subsequent CRM request must still pass ActiveOrganizationContextFilter and method security.

Switching: suspend CRM rendering, cancel old reads, discard pending mutation UI and tenant caches, validate target self-membership, then create a new client/remount keyed by account and organization. Tag every request/result with account+tenant generation; discard late success/error responses. Do not replay mutations in the new tenant. On failure, keep target data inaccessible; explicitly revalidate the prior tenant before restoring it. Keep chosen UUID in memory; any future persisted preference is only an untrusted hint requiring fresh validation. No frontend switch/picker is implemented until these contracts are approved and available.

## Exact backend changes required

1. Add `organization/dto/CurrentUserOrganizationResponse.java` with the minimal fields above; never serialize JPA membership/user entities.
2. Add a repository query in `OrganizationMembershipRepository` joining organization and filtering `user.id` from authenticated principal, ACTIVE status and `organization.archived=false`, across all roles. Use explicit ordering and a DTO projection or transaction-safe association fetching with open-in-view disabled. Add an equivalent self-membership lookup for target UUID. Existing uniqueness/indexes should be assessed; no schema change is inherently required.
3. Add `organization/service/CurrentUserOrganizationService.java` with authenticated/enabled principal resolution and transactional read-only queries. Its public methods must derive user ID internally, not accept an HTTP user ID. Do not reuse admin-only listByUser or remove its PreAuthorize. Discovery must not require trusted tenant context (which is unavailable before selection).
4. Add `identity/controller/CurrentUserOrganizationController.java` exposing exactly the two proposed routes; validate UUID and map errors to generic ProblemDetail. Preserve auth matcher authentication, UserEnabledSessionFilter and CSRF configuration. No broad new ActiveOrganizationContextFilter exemptions or CRM authorization changes are required.
5. Keep context validation and RBAC on every CRM request. Add tests below before merging. Audit denied tenant attempts without trusting a supplied UUID as authenticated tenant metadata; follow the existing platform-level denial pattern. Do not add membership mutations, invitation acceptance, organization creation or ownership changes to this proposal.

## Security acceptance tests for backend and host

Use real security filters with provisioned test data: two users, multiple tenants, all roles and each membership state. Discovery must return only the principal's active memberships and no archived organizations; VIEWER/SALES_USER may discover their own role without acquiring admin directory access. Reject arbitrary user impersonation parameters. Target lookup must return identical denial for nonexistent/foreign/archived/suspended/revoked membership. Disabled users must lose access even with an existing session. Revocation between discovery/selection and CRM request must fail. Header target/object target mismatch and foreign related IDs must fail. Existing admin-only membership methods, last-owner and role-assignment constraints must retain their tests.

Browser switching must discard stale reads and errors across account/tenant changes, preserve per-tab context, clear records on logout/401 and show local 403 without granting access. Cookie/CSRF tests and real deployment proxy checks are required separately. Source inspection and frontend mocks are not evidence these APIs or deployment work.
